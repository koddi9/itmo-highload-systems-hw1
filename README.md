# Items service: мониторинг метрик в Grafana

Домашнее задание 1 по курсу "Принципы построения высоконагруженных систем" (осень 2026)

Небольшой CRUD сервис на Spring Boot. В нём есть:
- собственная библиотека, которая собирает с REST-ручек метрики latency, traffic и errors
- генератор дашборда Grafana, который берёт список ручек из работающего сервиса
- фоновая нагрузка на k6

Ссылка на скринкаст: https://us04web.zoom.us/clips/share/1tv0p-jWR3ercJWd77_JYw 
(или Яндекс Диск: https://disk.yandex.ru/i/tYuRWcz6yVS-xA)

## Быстрый старт

Всё поднимается одной командой `docker compose up`.

```bash
cp .env.example .env
docker compose up
```

После запуска compose запускает сервисы в таком порядке:
1. `app-1`, `app-2`, Prometheus и Grafana проходят health-проверки.
2. `dashboard-generator` читает `GET /handlers` у обоих инстансов, загружает дашборд в Grafana и завершается с кодом 0.
3. Стартует `load` (k6) и за 3 минуты наращивает нагрузку до 40 RPS.

Мониторинг:
открыть <http://localhost:3000/d/items-http-metrics>. Логин и пароль заданы в `.env` (`GRAFANA_ADMIN_USER` / 
`GRAFANA_ADMIN_PASSWORD`)

Остановить стенд: `docker compose down`. (`-v`, если надо удалить и историю метрик Prometheus)

## Порты

Все порты опубликованы только на `127.0.0.1`.

| Сервис                 | Адрес                    | Назначение                              |
|------------------------|--------------------------|-----------------------------------------|
| Grafana                | <http://localhost:3000>  | дашборд `Items service: HTTP metrics`   |
| Prometheus             | <http://localhost:9090>  | targets, PromQL                         |
| `app-1` (pod-1, dc-1)  | <http://localhost:8081>  | первый инстанс сервиса                  |

## Метрики и лейблы

| Метрика                                                        | Тип       | Лейблы                                           | Что показывает  |
|----------------------------------------------------------------|-----------|--------------------------------------------------|-----------------|
| `app_http_request_duration_seconds_bucket` / `_sum` / `_count` | histogram | `pod`, `datacenter`, `method`, `route`, `le`     | latency         |
| `app_http_requests_total`                                      | counter   | `pod`, `datacenter`, `method`, `route`, `status` | traffic, errors |

- `pod`, `datacenter` берутся из переменных окружения `POD_ID` и `DATACENTER` и добавляются ко всем метрикам. Названия
  `instance` и `job` не подошли: их Prometheus проставляет сам.
- `method` + `route` определяют ручку. В `route` пишется шаблон пути (`/items/{id}`), поэтому число
  серий не растёт с числом id.
- `status` есть только у счётчика. В гистограмме он умножил бы число серий бакетов на число кодов ответа.
- Префикс `app_` отделяет эти метрики от встроенной в Spring Boot `http_server_requests_seconds`.

## Почему для latency выбран histogram

Перцентили должны оставаться корректными при агрегации по нескольким подам и датацентрам.
На дашборде можно выбрать All или любое подмножество.

Summary не подходит. Он считает квантили внутри каждого инстанса по скользящему окну. Квантили не складываются:
среднее или сумма p99 двух подов не равна p99 их объединённого трафика.

Histogram подходит. Бакеты - это счётчики, а счётчики можно складывать. `sum by (le)` по выбранным подам даёт бакеты
общего распределения, и `histogram_quantile` поверх них возвращает корректный перцентиль.

Точность ограничена шириной бакета, поэтому границы сгущены вокруг ожидаемых задержек: 1, 2.5, 5, 10, 25, 50, 75, 100,
150, 250, 500, 750 мс, 1, 2.5, 5 с.
